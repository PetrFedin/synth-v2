# Syntha V2 agent rules

- This repository is the only active Syntha V2 codebase.
- Never modify or import code from frozen legacy Syntha applications.
- Do not introduce an external identity provider; authentication belongs to Syntha V2.
- Cross-module imports go only through `public.mjs`.
- Business mutations require durable command IDs and transactional outbox events.
- Applied SQL migrations are immutable.
- Preserve organisation isolation, server-authoritative pricing and atomic inventory guarantees.
- Russian and English are mandatory interface languages; all new user-facing UI text must use the localization runtime.
- Do not add a visible button or status action without an implemented handler, capability check, API route, application method and automated interaction contract.
- Client validation must mirror domain boundaries but never replace backend validation.
- Transport retries for mutations must reuse the original idempotency key and must not retry domain HTTP errors.
- Destructive actions require explicit confirmation or a reason form.
- Preserve the browser dependency order: localization, shared DOM/API, capabilities and validation load before `app-core.js`; `app-start.js` loads last.
- Fashion KPI definitions, calculations, source mappings and publication rules must follow `docs/fashion-kpi/`. Do not duplicate KPI formulas in UI modules or silently redefine a governed KPI locally.
- Repository-native KPI mappings live in `docs/fashion-kpi/native-source-contracts.json`. If a mapped module export, runtime field, persistence table/container or lineage key changes, update the native source contract in the same change; `npm run verify` is expected to reject stale mappings.
- The durable KPI registry is append-only. `kpi_definition_versions`, `kpi_definition_release_events`, `kpi_source_mapping_versions`, `kpi_source_mapping_verification_events` and `kpi_definition_dependencies` must never be updated/deleted to rewrite history.
- Definition meaning and definition release status are separate histories. Changing `DRAFT/DEFINED/.../PRODUCTION_READY` appends a release event and must not create a fake formula version or mutate `kpi_definition_versions`.
- Physical mapping identity and mapping verification are separate histories. `MAPPED_UNVERIFIED -> VERIFIED` appends a mapping-verification event and must not create a fake mapping-set version or mutate `kpi_source_mapping_versions`.
- Formula version and mapping-set version are different concerns. Changes to KPI population, temporal basis, numerator/denominator, UOM algebra, aggregation, normalizer, estimator/quantile method, sign convention or other semantic meaning require a new formula version. A physical table/field/topic/adapter change with unchanged meaning requires a new mapping-set version instead.
- System-scope KPI definitions are platform governance objects and must not become tenant-editable merely because an organisation actor has normal membership. Organisation-scoped variants require explicit organisation isolation and governance.
- Native KPI implementations must resolve every logical input through a governed source contract or an explicit constant/policy input. Do not join by fuzzy SKU/date/text when exact immutable lineage IDs exist.
- A KPI is not production-ready until one coherent effective mapping set is verified, calculation/population tests pass, reconciliation passes where applicable, and owner/data-steward UAT is complete. The `PRODUCTION_READY` release event must carry evidence for these gates.
- Alias and blocked-umbrella KPI definitions must never own executable source mappings or emit independent observations.
- Percentage-like source fields must declare storage scale. In particular, do not treat a 0-100 percentage-points source as a canonical 0-1 ratio without an explicit adapter/reconciliation rule.
- Snapshot/versioned sources must define latest/effective/as-of selection before aggregation. Never sum historical snapshots as independent business facts.
- Due-cohort service KPI must keep open overdue cases in the denominator; closed-only denominators are prohibited unless the KPI explicitly measures completed-case duration rather than SLA compliance.
- KPI observations must preserve exact definition ID/formula version, effective mapping-set lineage, period/as-of, canonical UOM, DQ status, source/run lineage and restatement lineage; do not persist only a formatted dashboard value.
- Definition history, definition-release history, source-mapping history, mapping-verification history and observation/run history are separate immutable concerns. Do not overload one table/version/status field to represent several of them.
- Run `npm run verify` before publishing. It includes the governed fashion KPI methodology, repository-native source-contract validator and immutable KPI registry validator.
- Priority: stabilize existing commercial workflows before expanding fashion catalog/planning, PLM/BOM/samples, production, QC, logistics, landed cost, analytics and integrations.
