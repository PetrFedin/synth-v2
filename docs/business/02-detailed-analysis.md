## 1. Архитектура и зрелость

### 1.1 Устройство (факт)
- Один Node.js-процесс (`scripts/start.mjs`) обслуживает веб-интерфейс, API `/v2`, `/health`, `/ready`, `/openapi.json` (`CURSOR_START_HERE.md`).
- Слои: `src/core` (ошибки и т.п.), `src/modules/<домен>/public.mjs` (62 доменных модуля), `src/application/*-service.mjs`, `src/infrastructure/postgres-*`, `src/http`, `src/web/static-handler.mjs`, `src/runtime` (воркеры), `src/operations`, `src/acceptance`.
- Фронтенд — статический JS без сборщика: `public/index.html` подключает 21 CSS и ~90 скриптов `/ui/*.js` строго по порядку (`AGENTS.md`: локализация → DOM/API → capabilities/валидация → `app-core.js`; `app-start.js` последним).
- База: PostgreSQL 17, 183 миграции (`db/migrations/001…180_*`), checksum и advisory lock.
- Единственная runtime-зависимость `pg` (`package.json`); dev: TypeScript 7.0.2 и `@types/node` для проверки типов.
- Наблюдаемость: `docs/observability.md`, `ops/prometheus/syntha-v2-alerts.yml`.

### 1.2 Зрелость по домену (из `ARCHITECTURE.md` §16, без переоценки)
| Состояние | Домены |
|---|---|
| PROD-PROVEN | запуск/готовность/завершение процесса |
| IMPLEMENTED | аутентификация и организации, Product Identity, Production/Final Quality, Readiness, Commercial Projection, WholesaleOrder/OrderCommit, SupplyCommitment, инвентарь (ядро), ActualCost (общий и по SKU), распределение затрат, маржа/закрытие |
| IMPLEMENTED/PARTIAL | CommercialPublication, PriceListVersion, BuyerCatalog, BOM/измерения/образцы, сорсинг/техпак, ODS v1 |
| PARTIAL | PLM-планирование/стили, матрица цвет×размер, поставка/приёмка/восстановление поставщика, KPI на проде, сквозная живая приёмка Product→Margin |

Важно: «IMPLEMENTED» в проекте означает «путь есть в слое и покрыт тестами», а не «работал у клиента». Статус «PROD-PROVEN» присвоен только запуску процесса.

### 1.3 Что в работе (последние 30 коммитов)
Детерминированная оркестрация пересчёта при изменении изделия (change impact → resolution receipts → verified result references → recompute orchestration), операционные SLA исключений, канонический authority приложения, ИИ-инжиниринг продукта. Это AI Product Engineering — самая новая часть, ещё не доведена до пользовательского сценария целиком (в рабочем дереве есть незакоммиченные правки `recompute-orchestration.mjs`).

### 1.4 Тесты и проверки
- ~588 файлов в `tests/`, ещё `tests/postgres/` (15 файлов). `npm run verify` объединяет: isolation, architecture, postgres-контракт, UI, design-system, ODS-границы, i18n, MDM, KPI-методологию, типы, тесты.
- CI: `.github/workflows/ci.yml` (PostgreSQL 17), `verify.yml`, `product-commercialization-acceptance.yml`, `mdm-reference-data.yml`.
- Живая приёмка: `acceptance:collection`, `acceptance:product-readiness`, `acceptance:product-commercialization`, `acceptance:product-engineering` (`scripts/`).
- По `docs/audit-2026-09-21.md` (проверено автором выборочно): `npm run verify` давал 1495/1495; `validate:postgres` — текстовый поиск по SQL, к базе не подключается («34 tables» при 123 таблицах на тот момент); `validate:types` фиксирует 556 ошибок (`ops/type-baseline.json`) и следит, чтобы их не стало больше. Аудит датирован 2026-09-21; часть пунктов с тех пор могла быть исправлена, актуальность не проверялась.

## 2. Сильные стороны (с доказательствами)
1. **Дисциплина инвариантов.** Идемпотентные команды, outbox, неизменяемые миграции с checksum, изоляция организаций, серверная цена — записаны в `AGENTS.md` и частично проверяются в `verify`.
2. **Единый мастер продукта и «замороженные» снимки** (Readiness → Projection → Publication → BuyerCatalog → Order): историческое не пересчитывается задним числом (`ARCHITECTURE.md` §3.3).
3. **Fail-closed.** Недостающие доказательства блокируют, а не пропускаются (`AGENTS.md`).
4. **Честная самооценка.** Аудит, реестр долгов, статусы PARTIAL/GAP; документы признают слабые места.
5. **Минимум зависимостей** (`pg`), нет внешнего IdP.
6. **Билингвальность** RU/EN обязательна и проверяется `validate:i18n`.
7. **Широкая модель домена:** PLM + опт + склад + себестоимость + KPI в одной базе.

## 3. Слабые стороны
1. **Нет подтверждённого рыночного использования.** В репозитории нет данных о клиентах.
2. **Живая сквозная проверка не завершена** (`ACC-004`).
3. **Зелёные проверки сильнее выглядят, чем доказывают** (аудит, п. 1.4).
4. **Слабая изоляция тестов на реальных нескольких тенантах** (аудит: одна пара бренд—магазин).
5. **Сложность поддержки документации и CSS.**
6. **Нет e-mail и сброса пароля** — барьер для любого внешнего пилота.
7. **Интерфейс:** шрифт Arial, мелкий текст, 4008 `!important` (подробно в `03`).
8. **Публичный репозиторий** при коммерческой цели (решение владельца).
9. **Широкая дорожная карта** (`docs/SYNTH_V2_INTEGRATION_MASTER_PLAN_2026-10-01.md`: фазы GS1, DPP, EPCIS, LCA, OpenTelemetry, Arrow/Parquet) без привязки к спросу.
